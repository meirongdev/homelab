# k3s 升 1.36.6：升级本身无事，挖出五个静默坑

> 日期: 2026-11-20（Kyverno 迁移在 2026-11-19）
> 影响: 无线上事故。计划内停机：oracle 与 homelab 控制面各约 2 分钟，worker 上的媒体等钉死服务约 4 分钟。
> 根因: 见下五条，共同点是「平时不触发的路径从没被走过」：回滚命令、重启后的内核参数、升级闸门、脚本的 stdin。
> 相关: [k3s-cluster-upgrade](../runbooks/k3s-cluster-upgrade.md) · [security.md §5.2](../reference/security.md)

## 1 ☠️ runbook 的备份与回滚命令：glob 在 `sudo` 之前展开

**现象**：oracle 升级时 `sudo cp -a /var/lib/rancher/k3s/server/db/state.db* …` 报 `cannot stat`，
而此时 k3s 已经 `stop`，`set -e` 脚本退出，**集群停着、新二进制没装**。

**根因**：`server/db/` 与 `/root` 都是 root 专属目录，`state.db*` 由**普通用户的 shell** 展开，
展开不了就把字面量交给 `sudo cp`。回滚段的 `sudo rm -f …/state.db*` 更糟：**静默什么都不删**；
`sudo cp -a /root/k3s-preupgrade/state.db* …` 同样失败。回滚命令从没真正跑过，所以一直没人发现。

**修法**：glob 放进 root 的 shell：`sudo bash -c "cp -a …/state.db* …"`。runbook 四处已改。
停机之后才做的备份步骤，失败时必须先恢复服务再退出，别让脚本停在半路。

## 2 ☠️ kubelet 每次启动把 oracle 的 `panic_on_oops` 写回 1

**现象**：升完跑 `check-node-drift`，`panic_on_oops` 那项报 changed。实测运行时值是 **1**，
而 `/etc/sysctl.d/99-panic-on-oops.conf` 写的是 0。同时 `kernel.panic = 10`，正是 kubelet 的取值。

**根因**：`protect-kernel-defaults` 关着时，kubelet 每次启动会把一批内核参数写回自己想要的值，
其中就有 `panic_on_oops=1`，盖掉 sysctl.d。homelab 两台开着该项所以不受影响，oracle 没开。
于是**每次 k3s 重启都会重新武装** [AppArmor af_unix oops → 硬重启](2026-09-01-oracle-apparmor-af-unix-panic.md)
那条路径，而这个 oops 正是 09-01 之前三个月「宿主层重置」的成因。

**当下处置**：`sudo sysctl -w kernel.panic_on_oops=0`，已核对。**未根治**：下次 k3s 重启还会被写回。
候选做法（未实施）：k3s unit 的 drop-in 在启动后重设，或 timer 周期校正（仓库里 Cilium 5200 规则
已有 drop-in + timer 双防线的先例）。⚠️ 不能靠 `protect-kernel-defaults: true`：它要求该值就是 1，与目标相反。
runbook §9 ⑦ 已加验收项。

## 3 Kyverno v1.20：legacy 策略不再执行，升级闸门，新增 fail-closed webhook

v1.20 源码里已删掉 legacy `kyverno.io` 策略的准入/后台/报告路径，chart 3.10 在集群里还有 legacy
对象时**拒绝升级**。v1.19 官方只支持到 k8s 1.35，所以不迁就上不了 1.36。

- 4 条 ClusterPolicy 先迁成 `policies.kyverno.io` ValidatingPolicy，**并跑后逐资源对比两个 source 的
  PolicyReport**：其余三条 0 差异；`require-probes` 多出 25 个 CronJob 的 Pod，因为
  **`matchConstraints.objectSelector` 只在 webhook 层生效，后台扫描不认**，要再加 `matchConditions`。
- 升完核 webhook 的 `failurePolicy`：新增了 **`protect-generation-labels`，`Fail`**（chart 3.10 默认开），
  违背「安全组件 fail-open」。本仓库 0 条 generate 策略，它什么都不保护，已 `features.protectGenerationLabels.enabled=false`，
  `helm template` 实证整份渲染只差 `--protectGenerationLabels=true→false` 一行。
- 验收只验「被拦」不够，要配「不该被拦」的对照（合规 Pod、kube-system 里的 `:latest`）。

## 4 `ssh` 吞掉脚本剩余内容，控制面停着没装

把 stop → snapshot → install 写成 `bash -s <<EOF` 脚本，第一条 `ssh` 读了共享的 stdin，吞掉其余步骤：
只执行了 `stop`，之后什么都没发生，**输出看上去只是「没打完」**。核实状态后改用脚本文件，ssh 一律 `-n`
（唯一例外是用 stdin 传 token 的那一条）。判据：停服务的步骤之后必须有「失败即恢复」的分支，且先确认状态再续跑。

## 5 `KUBE_VERSION` 不在 V2 里

`scripts/render-manifests.py` 的 `KUBE_VERSION`（CI 渲染任务做 schema 校验用）注释写着「升 k3s 时同步改」，
但 V2 只强制三处 `k3s_version`。上次补丁升级就漏了，一直停在 1.35.8。这次已改到 1.36.6，runbook §11 列成第四处。

## 没出问题、但值得留底的

- k3s 发布说明里的「Bump gateway-api to 1.6.3」不影响本仓库：随 Traefik 打包，两集群都 `disable: traefik`，
  升完两集群 CRD bundle 仍是 v1.6.1（runbook §9 ⑧ 已加核对）。
- 升完 ArgoCD 有一个 App 短暂 `Unknown/Missing`（`ComparisonError: connection refused`），是控制面停机窗口里留下的旧结果，
  强刷后收敛。判据看 `reconciledAt` 与停机时间对不对得上。
- 改了 `argocd/applications/*.yaml` 要刷新的是 **root** App，不是子 App：子 App 对象本身由 root 管，
  刷子 App 会一直停在旧的 `targetRevision`。
