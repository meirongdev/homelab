# k3s 1.34.5 → 1.35.8 升级复盘（含 ZITADEL SSO 中断 ~7 分钟）

> 日期：2026-08-30
> 影响：**ZITADEL SSO 不可用约 7 分钟**（`auth.meirong.dev` 500，UTC 00:06–00:13）·
> homelab worker 上 7 个服务在 drain→uncordon 窗口内停机（jellyfin/navidrome/podcast/
> external-dns/sloth/opencost/cf-analytics-exporter）· homelab worker 的 k3s-agent
> 一度拒启。**无数据丢失，无回滚。**
> 根因：三条，**全部是升级 SOP 自身的缺陷**，不是 k3s 的问题 —— 见下。

## 结果

三节点全部 `v1.34.5+k3s1` → **`v1.35.8+k3s1`**（containerd 2.1.5 → 2.2.7）：
`oracle-k3s` · `k8s-node` · `k8s-worker-106`。顺序 oracle（金丝雀）→ homelab
控制面 → homelab worker。收尾 `just verify-node` **24/24 通过**，ClusterMesh 双向
connected，两集群未就绪 pod 归零，Vault 自动解封（`Sealed false`），ESO 全 SecretSynced。

⚠️ **停在 1.35，没上 1.36**：Kyverno 唯一 supported release v1.19 只覆盖到 k8s 1.35
（v1.20 预计 2026-11）。判据与查法见 [runbook §3.2](../runbooks/k3s-cluster-upgrade.md)。

## 根因一：漏了「谁把 k8s 版本当**输入**」这一类检查（造成 SSO 中断）

升级前的兼容性闸门只问了「组件**支不支持**新 k8s」（Cilium ✅ 1.33–1.36、CNPG ✅、
Kyverno ⚠️ 到 1.35），**没问「有没有组件把 k8s 版本读出来拿去拼别的东西」**。
这是两类完全不同的风险，后者不出现在任何支持矩阵里。

链条：

1. k3s 重启 → k3s helm-controller 重新 reconcile `HelmChart/zitadel`
2. chart 的 `tools.kubectl.image.tag` 默认留空 = **自动取集群 k8s 版本**
3. 于是去拉 `docker.io/alpine/k8s:1.35.8` —— 该镜像 tag 是**人工发布**的，
   跟不上 k8s 补丁节奏，当天最新只有 **1.35.6** → `not found`
4. `zitadel-setup` 是 **pre-upgrade hook**，hook 失败 → helm 回滚整个 release
5. `zitadel` 与 `zitadel-login` 两个 Deployment 被拆掉 → `auth.meirong.dev` 500

**这个坑每次升 k3s 补丁都会复发**，不是一次性的。

⚠️ 值得单独记的失败形态：**中断发生在升级"成功"之后约 3 分钟**。节点 Ready、
`k3s --version` 正确、pod 数回到 73 —— 我当时已经准备宣布 oracle 验收通过。
是例行 `get pods` 才看见一个 7 秒大的 ImagePullBackOff。**"升完看一眼节点就收工"
会完美错过它。**

**处置**：`cloud/oracle/manifests/zitadel/zitadel.yaml` 显式钉
`tools.kubectl.image.tag: "1.35.6"`（commit `0ce3f20`）。⚠️ oracle 是 arm64，
已核该 tag 是多架构 manifest list。推送后 ArgoCD 同步 → helm-controller 重跑 →
setup Job Completed → SSO 恢复。

**数据侧没有风险**：`zitadel-pg` 由 CNPG 单独管，不在 helm release 里，全程 Running。

## 根因二：k3s 安装脚本会**清空** agent 的 env 文件（造成 agent 拒启）

SOP 原文写着「`K3S_URL`/`K3S_TOKEN` 已持久化在
`/etc/systemd/system/k3s-agent.service.env`，无需重传」。**错。**

装完日志里那行 `[INFO] env: Creating environment file …` 不是"沿用"而是
**重新生成**，用当前 shell 环境覆盖。没重传 → 文件变空 →

```
level=fatal msg="Error: --server is required"
```

server 端的 `config.yaml` 会被保留，**但 agent 的 join 参数只活在这个 env 文件里，
装一次冲一次**。恢复没有回滚，把 token 从控制面管道过去重写 env 即可（命令见
[runbook §8 陷阱 ①](../runbooks/k3s-cluster-upgrade.md)）。

## 根因三：drain 不迁移硬钉在 worker 上的服务，只会让它们 Pending

SOP 原文写着「drain 会把 media 三个服务赶到控制面上，控制面同样挂得上」。**错。**

worker 上 7 个 Deployment 全部硬钉 `nodeSelector: {kubernetes.io/hostname:
k8s-worker-106}`，drain 之后**无处可去**：

```
0/2 nodes are available: 1 node(s) didn't match Pod's node affinity/selector,
1 node(s) were unschedulable.
```

所以 **drain 不是"平滑迁移"，是"这些服务开始停机"**，时长 = 整个 worker 升级窗口。
维护窗口要按这个算。（`uncordon` 后它们会自己回来，不需要 `rollout restart`。）

## 顺带修掉的两件事

- **Kyverno 3.8.2 → 3.9.0**（app v1.18.2 → v1.19.0）：v1.18 早已 EOL，测试范围到不了
  1.35。☠️ 不升的后果**完全静默** —— resource webhook 是 `failurePolicy: Ignore`，
  不兼容时不报错、不告警、pod 全 Running，只是 4 条 ClusterPolicy 悄悄不再拦。
  验证只能主动打一发该被拒的请求（`--dry-run=server` + `:latest` → 必须 Forbidden）。
  ⚠️ 顺序本该在升 k8s **之前**（v1.19 同时支持 1.33–1.35），实际是升完控制面后补的 ——
  当时控制面已停机，为省一轮停机没有回退。
- **三处 `k3s_version` pin** 改到 v1.35.8+k3s1（V2 检查强制三处一致）。

## 做对了的地方（下次照做）

- **oracle 当金丝雀**：三个坑里有两个先在 oracle 暴露，homelab 因此有备而来。
- **回滚点先于变更**：两台 homelab VM 的 `qm snapshot` 带 qemu-guest-agent 的
  freeze/thaw（文件系统一致）；oracle 无快照层，改用「停 k3s → 拷 state.db + 旧二进制」。
  三个坑全部就地修复，一次都没用上回滚 —— 但正因为有它才敢往下走。
- **脱离终端跑安装**：oracle 升级前 SSH 真的瞬断过一次，脚本 `setsid nohup` +
  日志落盘，断了不会留下"二进制换了、服务没起来"的半成品。
- **回滚点护栏**：脚本里 `[ -e /root/k3s-preupgrade/state.db ] && exit 1` —— 重跑会用
  升级后的 DB 覆盖升级前那份，而 oracle 没有 VM 快照兜底。
