# 106 入编 homelab worker：Tailscale 装到一半把节点踢下线，外加四个坑

> 日期: 2026-08-13
> 影响: 施工期波及，**prod 集群与线上服务全程无影响**。被影响的只有正在入编的
>       新节点自身（一度 SSH 不可达约 10 分钟，经 tailnet 抢救）。
> 根因: 见下四条，每条都是「配置写对了但顺序/取值错了，且失败是静默或误导性的」。
> 相关决策: [storage106-as-homelab-worker](../decisions/storage106-as-homelab-worker.md)

## 1 ☠️ `tailscale up` 与 ip-rule 防护之间有一个致命窗口

**现象**：`just setup-tailscale-worker` 跑到一半被 2 分钟超时切断，之后节点
`192.168.50.107` 的 SSH 完全不可达（`Operation timed out`），LAN 上 ping 也不通。

**根因**：剧本的顺序是 `tailscale up`（带 `--accept-routes`）→ 安装 ip-rule 收敛器。
`tailscale up` 一成功，节点就从 pve 学到它通告的 `192.168.50.0/24` 进 table 52；而
tailscaled 自带的 `5270: from all lookup 52` 优先级高于 `32766: lookup main`，
于是**节点自己 LAN 段的流量全被卷进隧道**，包括我正在用的 SSH。
收敛器里的 `5260 to 192.168.50.0/24 lookup main` 正是防这个——但它在窗口之后才装。

**抢救**：节点此时已在 tailnet 上（`100.74.162.97`），从那条路进去手工
`ip rule add ... priority 5200/5240/5260` 即恢复。

**教训**：给**新节点**跑这个剧本时，那个窗口是真实存在的；不要在窗口内中断它。
若已中断，别去 LAN 上找它——从 tailnet 进。

## 2 ☠️ ip rule 优先级 5250 被 tailscaled 自己占着

第一版把「控制面网段走 main」写成了 5250，实际它是 tailscaled 的
`from all fwmark 0x80000/0xff0000 unreachable`。tailscaled 占 **5210 / 5230 / 5250 / 5270**，
留给我们的空位只有 **5200 / 5220 / 5240 / 5260**（且必须 < 5270 才抢得到 `lookup 52`）。
现取 **5240**。

## 3 ☠️ `disable-kube-proxy` 是 server-only flag，写进 agent 会 fatal 拒启

```
level=fatal msg="Error: flag provided but not defined: -disable-kube-proxy"
```

集群用 Cilium `kubeProxyReplacement`，直觉上 agent 也该声明一遍——**不对**。
agent 从 server 的集群配置继承「kube-proxy 已禁用」。实测入编后
`pgrep -x kube-proxy` 为空、无 `KUBE-SERVICES` 链，无需任何声明。

## 4 既存缺陷：k8s-node 缺自己网段的 ip rule，inventory 的 ProxyCommand 一直是坏的

**现象**：剧本用 `delegate_to: k8s-node` 取 node-token 时
`Connection timed out during banner exchange` / `Connection to UNKNOWN port 65535`。
手工跑 inventory 里那条 ProxyCommand 同样失败。

**取证**：

```
pve# ip neigh show 10.10.10.10     → REACHABLE，MAC 正确（L2 没问题）
pve# nc -z 10.10.10.10 22          → FAIL
pve# nc -z 10.10.10.10 6443        → FAIL
k8s-node# ip route get 10.10.10.1
  10.10.10.1 dev tailscale0 table 52 src 100.94.186.7      ← 回程进了隧道
```

k8s-node 有 `5200`（100.64/10）和 `5260`（192.168.50.0/24）两条防护，**唯独没有
`10.10.10.0/24`**——它自己那个网段。所以 pve 发起的 SYN 从 vmbr0 进来，SYN-ACK 从
隧道出去，非对称直接失败。

**为什么一直没人发现**：日常都用 Tailscale 地址访问 k8s-node，没人走那条 ProxyCommand。
但 `k8s/ansible/inventory/hosts.yaml` 里它是 k8s-node 的**唯一声明访问路径**，
意味着所有 `hosts: k8s_masters` 的剧本目前都连不上。

**本次的处理**：**未修根因**（改 prod 路由不在本次委托范围）。改为让
`just join-worker` 经 k8s-node 的 Tailscale 地址取好 token 再传进剧本，
剧本用 `assert` 校验而不再 `delegate_to`。

⚠️ **待办**：给 k8s-node 补 `5240 to 10.10.10.0/24 lookup main`（与 worker 同款），
或把 inventory 里 k8s-node 的访问路径改成 Tailscale。二选一，否则
`hosts: k8s_masters` 的剧本继续不可用。

> **后记（2026-08-13 当日）**：已按第一种修——5240 统一进 `setup-tailscale.yaml`
> 默认清单（控制面/worker 同一份），手工加规则后 ProxyCommand 路径实测恢复，
> 剧本重铺固化。同场还抓出了收敛器的渲染 bug，见
> [2026-08-13-iprule-guard-render-bug.md](2026-08-13-iprule-guard-render-bug.md)。

## 5 两个小坑

- **Tailscale API 拒绝 key 描述里的括号/连字符**：`keys: description had invalid
  characters (400)`。只用字母数字和空格。
- **新节点没有 `/etc/systemd/networkd.conf.d/`**：控制面上早就有，
  `copy` 直接报 `Destination directory does not exist`。剧本已补 `file: state=directory`。

## 一个读数陷阱（差点误判）

验收时 `pgrep -f kube-proxy` 报「有」——那是匹配到了**我自己那条含该字符串的 shell 命令**。
用 `pgrep -x` 才准。同理 `nslookup` 在 curl 镜像里返回非零（busybox 对 AAAA 失败返回
非零的老毛病），而同一个 pod 里**按 Service 名字 curl 两个服务都拿到 200**——
DNS 其实是通的。**判据要选不会自我污染、不会假阴性的那个。**
